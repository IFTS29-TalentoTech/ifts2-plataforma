# B01 — Acceso efectivo por capacidades

Base: `develop` `bc610d09a288f2ffd4a88d9d98cd0891dbcc2390`, independiente de B08 y B04. Las capacidades señaladas seguían bloqueadas.

## Causa y corrección

Navegación y páginas contenedoras exigían un permiso distinto del que autorizaba la acción. Además, Horarios montaba las dos secciones sin discriminar capacidades, y leer ciclos o categorías de los selectores exigía permisos de administración de esos catálogos.

- `lib/nav.ts` define las capacidades de cada contenedor; el menú y las páginas usan la misma decisión. Tras iniciar sesión, `/panel` conduce a una pantalla autorizada cuando el rol no puede leer el resumen.
- Configuración admite usuarios, contenido, enlaces e integraciones independientemente de ajustes. Los datos institucionales, su guardado y sus consultas solo se montan con `settings:manage`; la gestión de usuarios ya no depende de que carguen esos datos. Las pestañas visibles eligen un valor inicial permitido y se reinician cuando cambian las capacidades.
- Horarios admite gestión de llamados, creación de ciclos y elección del ciclo público independientemente de gestionar grillas. Solo monta la sección autorizada. El llamado oculta la carga de documentos si no se autorizó esa capacidad.
- Publicaciones separa moderación de redes y gestión de propias. Solo se montan las pestañas autorizadas, sin consultas de recursos ajenos; la eliminación de propias exige además `publications:delete`.
- La API permite leer ciclos a sus consumidores autorizados y categorías a los formularios de autoría/moderación. Crear/editar ciclos, elegir el público y administrar categorías conservan sus permisos específicos. No se otorga ningún permiso adicional al rol.
- Se evitan consultas al resumen desde la estructura del panel o la moderación cuando no existe `dashboard:read`. Los roles tradicionales conservan su navegación.

## Pruebas

Antes: ocho casos unitarios de navegación fallaron; cuatro capacidades recibían 403 al leer ciclos; tres casos adicionales reprodujeron 403 al leer categorías desde la API anterior. En navegador, los siete permisos del pedido y dos combinaciones crearon sus roles desde SUPERADMIN y recibieron correctamente sus permisos, pero carecían del enlace necesario. Un caso adicional de `terms:setPublic` falló inicialmente en el selector del arnés (etiqueta corregida); no se atribuye ese fallo al producto.

Las pruebas nuevas están en:

- `apps/web/test/delegated-navigation.test.ts`: capacidades, denegación por defecto, coherencia de menú/página y roles tradicionales.
- `apps/api/test/api/delegated-term-access.test.ts`: lecturas necesarias permitidas, escrituras ajenas 403 y acceso anónimo 401.
- `apps/web/cypress/e2e/panel-b/delegated-capabilities.cy.ts`: doce casos en Chromium. Ocho permisos individuales y dos combinaciones se configuran desde la UI de SUPERADMIN, se asignan a cuentas ficticias y se verifican con `/auth/me`. Cada caso abre el destino desde el inicio, por URL y por menú, ejecuta acciones autorizadas y prueba rechazos API. Incluye administración de usuarios sin ajustes, moderación sin gestión de propias, cambio de permisos en una sesión existente y gestión de propias sin moderación ni eliminación.

Comandos:

```sh
pnpm --filter @ifts2/web test
pnpm --filter @ifts2/api exec vitest run --project integration test/api/delegated-term-access.test.ts
CYPRESS_BASE_URL=http://localhost:3302 pnpm --filter @ifts2/web exec cypress run --browser chromium --headless --spec cypress/e2e/panel-b/delegated-capabilities.cy.ts
```

Resultados iniciales posteriores: API completa 663/663; web 27/27; shared 80/80; doce E2E nuevos aprobados. Se completa además la regresión de horarios y roles tradicionales antes del commit.

## Alcance y límites

Los controles de la API son definitivos: una pestaña o una URL nunca otorga permiso de escritura. Las sesiones existentes reciben los permisos actuales en el siguiente pedido; la navegación o recarga vuelve a representar la UI con ellos, sin un nuevo login. No se agrega sincronización por push entre navegadores.

Se conservan anti-escalada de usuarios, permisos adicionales para acciones destructivas y reglas de elegibilidad. No se crean pantallas nuevas para los hallazgos excluidos (categorías, auditoría u otros). Las pruebas usan únicamente las bases nuevas del contenedor `fixes-b-pg`, proveedores ficticios y cuentas de prueba.

Resultado final: lint, typecheck y build aprobados; 32/32 E2E de la selección final (12 nuevos, 10 de horarios/llamados y 10 de roles/usuarios tradicionales), en Chromium. Las suites preexistentes se conservaron sin cambios.
