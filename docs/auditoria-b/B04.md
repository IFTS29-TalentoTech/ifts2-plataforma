# B04 — Confirmaciones HTTP verificables

Base: `develop` `bc610d09a288f2ffd4a88d9d98cd0891dbcc2390`, independiente de B08. El defecto seguía presente.

El cliente absorbía errores JSON y devolvía `undefined` o un objeto incompatible como si hubiera confirmado una mutación. Los consumidores anunciaban éxito al resolver esa promesa.

## Corrección

`src/lib/api.ts` de web ahora exige tipo de contenido JSON, cuerpo parseable y contrato de salida para las mutaciones. `mutation-contracts.ts` registra los estados HTTP y los campos de confirmación de todas las familias usadas por la web: publicaciones, redes, usuarios, roles, contenido, ajustes, integraciones, documentos, horarios, llamados, avisos, enlaces, plantel, galerías y contacto. Los enums provienen de shared. No se descartan campos adicionales. Las operaciones con 204 (autenticación y borrados) lo admiten explícitamente; publicar exige JSON. Una mutación sin contrato se bloquea antes de enviar la solicitud.

Los errores HTTP conservan su estado. Fallas de transporte, de lectura del cuerpo, de contrato y 5xx de mutaciones se informan como resultado desconocido: el servidor podría haber guardado los cambios. El mensaje pide verificar antes de reenviar. Los 4xx siguen siendo rechazos y se conserva el motivo útil de las integraciones.

`confirm-publication.ts` valida identidad, estado solicitado y fechas de publicar/pausar/programar/reactivar. Ante un resultado incierto hace un único GET sin caché. Solo confirma éxito si la lectura prueba el estado esperado. Nunca reenvía el POST. Si también falla la lectura, mantiene la incertidumbre. Lo usan `own-publications-tab.tsx` y `vigencia-dialog.tsx`; `features/panel-a/lib/errors.ts` conserva el mensaje en los demás consumidores.

## Evidencia y pruebas

- Prueba previa del cliente: 5 fallos (200 HTML/vacío/JSON roto/objeto incompatible y 204 al publicar).
- Navegador anterior + API real: los cuatro cuerpos 200 inválidos mostraban éxito con fila DRAFT; cortar la conexión después de `route.fetch()` dejaba PUBLISHED sin confirmación recuperable.
- `test/api-responses.test.ts`: contratos, identidad/estado, 204 permitido/prohibido, 500/403, transporte y lectura interrumpidos, recuperación tras commit, consulta también fallida, fechas distintas, otras familias y ausencia de reintentos.
- `cypress/e2e/panel-a/http-confirmations.cy.ts`: ocho recorridos con persistencia real, incluidos cuerpo perdido después del commit y comprobación de un único POST.
- Arnés externo Playwright `/workspace/evidence-b/b04-browser.mjs`: siete casos, incluida conexión cortada tanto antes de la mutación como después de que la API confirmara el commit. Resultado posterior: siete conformes; nunca éxito con DRAFT y siempre un solo POST.

Reproducir con una API y web locales conectadas exclusivamente a una base descartable y usuarios demo:

```sh
pnpm --filter @ifts2/web test
CYPRESS_BASE_URL=http://localhost:3301 pnpm --filter @ifts2/web exec cypress run --browser chromium --headless --spec cypress/e2e/panel-a/http-confirmations.cy.ts,cypress/e2e/panel-a/publicaciones.cy.ts
```

La suite de regresión no se modifica para aceptar respuestas inválidas. Durante implementación detectó un enum incorrecto de la nueva validación y pérdida del motivo de un 502; ambos se corrigieron en producto antes de repetirla.

## Límites

Un contrato válido es la confirmación del servidor, no una garantía frente a un servidor que mienta deliberadamente. La consulta posterior confirma el estado observado, sin atribuir qué sesión produjo ese estado. La creación con respuesta perdida no tiene identidad recuperable: se comunica incertidumbre sin reintentar; incorporar idempotencia a las altas pertenece al hallazgo B11 y queda fuera de este PR. Las nuevas mutaciones deben registrar su contrato y prueba correspondiente.

Los siete casos adicionales de Playwright también conformes. Las pruebas nuevas recuperan las fechas usando el mismo inicio/fin de día de Buenos Aires que la API.
