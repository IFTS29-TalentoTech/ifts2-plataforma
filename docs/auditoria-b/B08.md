# B08 — Integridad de horarios

Base verificada: `develop` `bc610d09a288f2ffd4a88d9d98cd0891dbcc2390` (posterior al SHA auditado). El defecto seguía presente.

La lectura previa de `published` y `documentId` autorizaba un UPDATE incondicional después de que otra transacción cambiara esos valores. PATCH, publish y unpublish ahora usan una precondición atómica sobre ambos campos. PostgreSQL comprueba esa condición al actualizar la fila; Prisma P2025 se traduce a 409. La auditoría permanece en la misma transacción: el perdedor no escribe ni deja un evento de éxito. No hay reintento automático ni migraciones o limpieza de datos existentes.

Archivos: `apps/api/src/modules/schedules/index.ts` y `apps/api/test/api/schedules-concurrency.test.ts`.

## Reproducción y verificación

La nueva prueba de integración retiene ambas lecturas reales de Prisma hasta que leen el mismo estado y libera el segundo UPDATE solamente después de recibir la respuesta del primero (commit incluido). Prueba ambas órdenes y ciclos públicos/no públicos. Antes: 4/4 fallan porque ambas respuestas son 200. Después: 4/4 pasan, con 200+409, fila final válida, notas sin cambios parciales, auditoría única y DTO coherente.

Ejecutar con PostgreSQL descartable marcado según `apps/api/test/helpers/test-database.ts`:

```sh
pnpm --filter @ifts2/api exec vitest run --project integration test/api/schedules-concurrency.test.ts test/api/schedules-exam-calls.test.ts
```

Resultados: 17/17 pruebas específicas; suite API completa 659/659; shared 80/80; web 17/17; lint, typecheck y build completos aprobados. Cypress `panel-b/e2e-08-horarios.cy.ts`: 10/10, Chromium, 390 y 1440 px. Cypress requirió ejecutarse fuera del sandbox porque su smoke test terminaba con SIGTRAP dentro de él.

Aislamiento: contenedor nuevo `fixes-b-pg`, PostgreSQL 17; integración en `ifts2_test` con marca descartable y puerto 5433 interno; navegador en la base nueva `fixes_browser`, puerto 55434 externo. El contenedor preexistente `ifts2-db` no se modificó ni se usó. Correo console, Instagram fake, usuarios ficticios. Logs de la sesión en `/workspace/evidence-b/b08-*.log`.

Límite: es control de concurrencia de las operaciones de horarios de la API; no sustituye las reglas de autorización, ni resuelve otros hallazgos de concurrencia de la auditoría. Ante 409 hay que recargar y revisar antes de volver a operar.
